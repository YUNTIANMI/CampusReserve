- [x] 资源不存在
- [x] 参数错误
- [x] 非法时间

验收：
用户可以成功预约可用时间段。

验收结论（2026-09-15 实测）：
- 端到端测试 61/61 通过（`tools/e2e/e2e-phase6.js`），
  Phase 1 / Phase 2 / Phase 3 / Phase 4 / Phase 5 回归 36/36、47/47、65/65、81/81、64/64
- Booking 数据模型沿用 `types/booking.ts` 的 `Booking`（含 `id` / `resourceId` / `resourceName` /
  `location` / `date` / `startTime` / `endTime` / `status` / `createdAt`）与入参 `CreateBookingPayload`
- 前端提交：详情页 `onSubmit` 接入 `services/booking.ts` 的 `createBooking()` → `POST /api/bookings`
  （Phase 10 接真实后端，本阶段由 `services/mock-booking.ts` 顶替）；
  提交中按钮变为「提交中…」且不可再点，成功后 `wx.showToast` 提示并跳转「我的预约」
- 提交前检查的五项分工：**已登录**与**日期/时间合法**由客户端先判（不等一个来回就能给出原因），
  **资源存在**与**时间段仍可用**由服务端判（页面上的时段是加载时的快照，可能已过期或被别人约走），
  两端共用 `utils/booking.ts` 的同一份规则
- 冲突检查三层：请求的时段不在开放范围内 → 参数错误；时段状态非 `AVAILABLE` → 冲突；
  同一资源同一日期同一开始时间已有预约 → 冲突。开发期预约表落在缓存键 `CR_MOCK_BOOKINGS`，
  可用时间段会叠加它，因此「刚被约走的时段」立刻显示为已约满，不会自相矛盾
- 成功提示：toast「预约成功」+ 800ms 后跳转「我的预约」；跳转前清空已选时段，
  返回详情页时（`onShow`）重新拉取时段，避免用户对同一格再点一次必然失败的按钮
- 失败提示按错误码分流，页面内提示条 + toast 同时给出原因
  （toast 会消失，而「该时段已被预约」是需要用户据此改变行为的提示）：
  - `409001` 冲突 → 「该时间段已被预约，请选择其他时段」并**立即重取时段**
  - `404001` 资源不存在 → 「该资源不存在或已下架」并重新加载详情，落到 empty 态
  - `400001` 参数错误 / `400002` 非法时间 → 给出具体原因，保留已选时段可直接重试
  - `401` 登录态失效 → **清掉本地登录态**并引导重新登录（继续保留「已登录」只会让用户反复碰壁）
  - 网络异常 → 「网络连接失败」且保留已选时段，可原样重试（与上述业务失败区分开）
- 客户端对「已过时时段」的兜底：用户在详情页停留久了，加载时的时段快照可能已过期，
  这条只能在提交那一刻重新判定（E2E 用「把预约数据源打成网络失败、提交后仍看到『已过时』」
  证明该请求根本没发出去）

验收结论（2026-09-16 实测）：
- 端到端测试 63/63 通过（`tools/e2e/e2e-phase7.js`），Phase 1 ~ Phase 6 回归
  36/36、47/47、65/65、81/81、64/64、61/61，七套合计 **417** 项断言全绿
- 列表：`GET /api/bookings/my`（Phase 10 接真实后端，本阶段由 `services/mock-booking.ts`
  的 `mockGetMyBookings()` 顶替），**入参不含 userId**——用户身份由服务端从请求凭证解析，
  「只能看到自己的预约」因此是服务端边界，前端无从伪造，也更不需要在前端过滤
- 一次请求全量、页签切换只做本地过滤：三个页签是同一份数据的不同视图，
  每切一次都发请求只会让用户等，且「已完成」是按当前时刻派生的，两次请求之间会漂移
- **状态派生**：`utils/booking.ts` 的 `resolveBookingStatus()` 把「预约时段是否已结束」
  折算成展示状态——服务端只记录显式变更（创建 / 取消），「时段过去了」没人去点一下，
  直接读 `status` 会让昨天约的场地今天仍挂在「待使用」里。
  刻意**不改数据**：让 `GET` 产生写副作用不干净，真实后端哪天自行推进了也不会冲突
- 排序方向刻意不同：待使用按时间**升序**（最近要用的在最上面），
  已完成 / 已取消按**降序**（历史里越近的越可能还想点开看）
- 未登录时**不发起请求**：没有凭证时服务端无从判断身份，请求必然 401，
  既然页面已经知道未登录，就不该先转一圈 loading 再落到引导上
- 登录态失效时清掉本地登录态并引导重新登录（与详情页提交时同一条原则）
- `BookingCard` 组件与 `ResourceCard` 同构：只展示与抛 `cardtap`，不硬编码路由
- **预约详情复用 `/bookings/my` 再按 id 查找**，不新增 `GET /api/bookings/{id}`：
  技术设计 §3 的接口清单里没有它，且 `/my` 本来就只返回本人的数据，
  查不到即等于「不存在或无权访问」，无需另写一遍归属校验
  （代价是每次进详情拉一次全量列表，已记入 `PROJECT_MEMORY.md` 已知问题）

# Phase 8：取消预约

- [x] `DELETE /api/bookings/{id}`
- [x] 取消确认
- [x] 状态更新
- [x] 时间段恢复可用
- [x] 返回页面刷新

验收：
用户只能取消自己的有效预约。

验收结论（2026-09-16 实测）：
- 端到端测试 73/73 通过（`tools/e2e/e2e-phase8.js`），Phase 1 ~ Phase 7 回归
  36/36、47/47、65/65、81/81、64/64、61/61、63/63，八套合计 **490** 项断言全绿
- 取消：`DELETE /api/bookings/{id}`（Phase 10 接真实后端，本阶段由
  `services/mock-booking.ts` 的 `mockCancelBooking()` 顶替），**入参只有 id**——
  用户身份由服务端从凭证解析，并在本人名下的记录里按 id 查找；
  查不到即等于「不存在或无权访问」，需求 §4.7 与技术设计 §11 第 6 条
  「不得取消其他用户预约」因此不需要前端做任何归属判断
- **只有「待使用」能取消**：判据是 `utils/booking.ts` 的派生状态
  （`canCancelBooking()` 复用 `resolveBookingStatus()`），不是 `status` 原值。
  已结束的预约会派生为「已完成」，按钮随之消失——与列表页永远用同一把尺子，
  不会出现「这一页说已结束、那一页还能取消」的自相矛盾
- **二次确认**：取消后原时段会释放给他人，不是「取消了还能原样约回来」的操作，
  一次误触的代价不该由用户承担。确认框点「再想想」时什么都不发生（不发请求）
- **取消成功后停在本页**：用户需要亲眼看到「已取消」；自动跳走会让人怀疑有没有成功。
  返回「我的预约」时的刷新由它的 `onShow` 自然完成，本阶段不新增任何刷新标记
- **取消后时间段恢复可用**：不需要额外清理动作——`isSlotBooked()` /
  `overlayBookedSlots()` 从一开始就把 `CANCELLED` 排除在占用之外。
  端到端用「预约后该时段 BOOKED → 取消后恢复 AVAILABLE」验证，而不是只断言数据字段
- **失败分流**：网络异常保留按钮并在页面上留下原因（可原样重试）；
  查不到（`404001`）落到 empty 态不给重试；状态冲突（`409001`）说明页面数据已过期，
  直接重新拉详情把它刷成真实状态；登录态失效只提示，清态与引导交给「我的预约」页
- **服务端校验是权威**：端到端刻意「绕开 UI 直接调 `performCancel()`」，
  验证已结束 / 已取消的预约即使绕过按钮也拦得住——客户端的按钮只负责不出错

阶段边界（刻意留在后续阶段）：
- `DELETE /api/bookings/{id}` 的真实后端实现属于 Phase 10，本阶段由开发期数据源顶替

验收结论（2026-09-16 实测）：
- 端到端测试 69/69 通过（`tools/e2e/e2e-phase9.js`），Phase 1 ~ Phase 8 回归
  36/36、47/47、65/65、81/81、64/64、61/61、63/63、73/73，九套合计 **559** 项断言全绿
- **统一反馈层 `utils/feedback.ts`**（新增）：`toastSuccess` / `toastError` / `toastInfo` /
  `toastNavigateFailed` / `confirm(options): Promise<boolean>`。
  页面里不再出现裸的 `wx.showToast` / `wx.showModal`。这不是为了少写几行代码，
  而是让**同一类反馈在所有页面长得完全一样**：成功 / 失败 / 中性的图标与 2000ms 停留时长、
  危险操作的确认按钮色，都只有一处定义。端到端逐页比对模态框的
  `title` / `content` / `confirmText` / `cancelText` / `confirmColor` 与 toast 的
  `icon` / `duration`，防止某一页悄悄「自己写一套」。
- **`confirm()` 的 `fail` 分支返回 `false`（安全方向）**：弹窗弹不出来时既不能卡在「等待确认」，
  也不能当成用户点了确认。端到端用探针主动触发 `showModal:fail`，验证
  「不发请求、不给成功提示、页面状态不变」。
- **「等待确认」与「请求进行中」是两个阶段，各自防重复**：确认框 Promise 化后，`await` 期间
  `canceling` 还没被置位，只靠它拦不住「连点两次弹出两个确认框」，因此预约详情页另设
  `confirming`。两个标记分开，才不会出现「框还挂着按钮就转圈」。
- **危险色按操作是否可逆区分**：取消预约（原时段会被释放给别人，不可逆）的确认按钮用
  `#f5222d`；退出登录（再登一次就回来）**不用**危险色。端到端两条都断言。
- **Toast / Modal 的形态齐备**：`loading-state` / `empty-state` / `error-state` 三个组件
  从 Phase 1 起就在每个页面按四态渲染，本阶段未新增组件，而是把散落在各页的**文字反馈**
  收敛到一处出口。
- **「页面返回刷新」沿用 `onShow` 自然刷新**，不新增刷新标记：从预约详情返回「我的预约」、
  从详情返回列表都会自动重拉一次。这是 Phase 6 / 7 的既定取舍，本阶段只补验证。
- **必要缓存：最近使用的筛选条件 `store/preference.ts`**（新增，键 `CR_LAST_CATEGORY`）。
  优先级是 **URL 参数 > 本地缓存 > 空（全部）**：带参数进入说明是明确意图（从首页某个分类点进来），
  必须以参数为准**并顺手更新缓存**——否则会出现「刚在列表里看过自习室，回首页点『查看全部』
  却落回球场」这种用户无法理解的现象。非法缓存值归一化为「全部」，不落到错误态。
  端到端覆盖「URL 优先」「重复点击当前分类不重写缓存（提前 return 分支）」「非法值归一化」。
- **下拉刷新补齐到「我的预约」**（`enablePullDownRefresh: true`）。
  **未登录等异常路径同样要收起刷新动画**——用户做了主动动作就一定要有回应。端到端用探针
  接管 `wx.stopPullDownRefresh` 计数来断言（含未登录分支），而不是去看渲染层。
  另：下拉刷新**只重拉数据、不重置页签**，页签是用户的选择，不该被刷新动作抹掉。
- **屏幕适配**：`.cr-page` 底部改为两段式
  `padding: … var(--cr-space-xl); padding-bottom: calc(var(--cr-space-xl) + env(safe-area-inset-bottom, 0px))`，
  给全面屏机型留出 home indicator 的高度；**必须是两条独立声明**——写在一起时 `env()`
  一旦不被支持，整个 `calc` 会失效，反而把下内边距变成 0，比不写更糟。
  全局 `backgroundTextStyle` 由 `light` 改为 `dark`：背景是浅灰（`#f5f6f8`），
  浅色下拉圆点在浅底上看不见。
- **真机测试未做**：`04` 原计划里列了真机验证，但它需要开发者用开发者工具「预览」扫码到自己的
  手机上，AI 环境只能跑到模拟器。**在此明确说明，不由测试脚本代称通过**；
  真机验证顺延到 Phase 11，或在 Phase 9 收尾时由开发者补做。

阶段边界（刻意留在后续阶段）：
- 真实图片资源（`imageUrl` / `avatarUrl`）仍不提供，占位方案沿用，属 Phase 12
- 骨架屏未引入：当前三个状态组件在加载态已有明确反馈，且骨架屏需要真实图片尺寸信息
  （与上一条冲突），在拿到真实图片之前做只能做出假的骨架
